# Records are keyed by their Center, and corrections append history

Every record about a Center's operations has a key in the one main table that starts with the Center's ID, and every secondary-index key does too. Keys are built by one module that can't build a Center key without a Center, so no query can cross Centers by accident. Only five partitions sit outside a Center: people, logins, Organizations, Stripe accounts and an operations-only list of Centers. None of them holds anything about a child. Corrected records, such as Sign-in/out, keep a current head plus immutable history items written in the same transaction, so the original is never overwritten. A record never changes partition, so a correction that would move it to another day is done as a void plus a new record. Records take device-created ULIDs and save idempotently (ADR 0004). This was chosen over separate tables per area or per Center, which isolate data more strongly but multiply tables and IAM. The tradeoffs: an Owner's view and scheduled jobs work one Center at a time, every Center needs its own schedules, and the key layout is very costly to change once real data exists. See `docs/data-model.md` for the full design.
